PRÉPARATION DE LA DÉMO

Tout ce qu'il faut lancer, ouvrir et dire,dans l'ordre.

Cette page est ma liste de contrôle pour la soutenance. Le modèle tourne sur un GPU RunPod derrière vLLM ; l'API et le monitoring tournent sur mon poste, branchés sur ce GPU. Je montre un parcours complet : un cas saisi dans l'API, la priorité et l'explication, le trafic qui apparaît dans Grafana, puis la limite connue du modèle. Compter 30 minutes de préparation et environ 1 $ de GPU.

SÉCURITÉ Aucune clé à l'écran.

Ne pas ouvrir .env pendant la démo, ne pas afficher la page Secrets de RunPod ni les variables d'environnement d'un pod. Si une clé apparaît, la régénérer après la séance. Les cas présentés sont fictifs : RunPod n'est pas un hébergeur certifié HDS.

02

Lancer le service, 30 minutes avant

Le démarrage de vLLM prend plusieurs minutes (téléchargement du modèle depuis Hugging Face). Les commandes sont en PowerShell, depuis la racine du projet ; remplacer <pod-gpu> par l'identifiant du pod.

T-30 • GPU

Déployer le pod vLLM

RunPod › Deploy, template triage-vllm, GPU en Europe (RTX PRO 4000 ou A5000). Dans les logs, attendre Application startup complete et noter la version de vLLM et le temps de démarrage.

T-20 • Contrôle

Vérifier que le modèle répond

Charger la clé dans le terminal sans l'afficher, puis interroger la liste des modèles : la réponse doit contenir triage-qwen3.

T-15 • Poste

Lancer l'API et le monitoring

Renseigner dans .env l'adresse du pod (deux lignes), puis démarrer l'API, Prometheus et Grafana avec Docker Compose.

T-10 • Vérifier

Cibles et premier appel

Prometheus › Status › Targets : API et vLLM « UP ». Un premier appel /triage pour réveiller le service, puis la rafale des dix cas pour remplir Grafana.

T-5 • Onglets

Ouvrir les onglets dans l'ordre

Voir la section suivante. Zoom du navigateur à 125 %, notifications coupées, terminal en grande police.

PowerShellà lancer dans l'ordre
# 1. Clé vLLM chargée depuis .env, sans l'afficher
$env:VLLM_API_KEY = (Get-Content .env | Select-String '^VLLM_API_KEY=').ToString().Split('=',2)[1]

# 2. Le modèle répond ?
curl.exe -H "Authorization: Bearer $env:VLLM_API_KEY" https://<pod-gpu>-8000.proxy.runpod.net/v1/models

# 3. Dans .env (éditeur, hors écran) :
#    INFERENCE_BACKEND=vllm
#    VLLM_BASE_URL=https://<pod-gpu>-8000.proxy.runpod.net/v1
#    VLLM_METRICS_SCHEME=https
#    VLLM_METRICS_TARGET=<pod-gpu>-8000.proxy.runpod.net

# 4. API + Prometheus + Grafana sur le poste
docker compose --profile monitoring up -d api prometheus grafana

# 5. Santé de l'API (attendu : model_ready true)
curl.exe http://127.0.0.1:8000/health

# 6. Rafale des dix cas inédits (remplit Grafana, sert de répétition)
uv run python benchmarks/demo_cas_inconnus.py --mode api --api-url http://127.0.0.1:8000

Mesure de latence du service (à faire une fois, hors démo) : uv run python benchmarks/eval_test_gele.py --mode vllm --vllm-url https://<pod-gpu>-8000.proxy.runpod.net/v1.

04

Le déroulé, en dix minutes

0:00 • Contexte

Le besoin du CHSA

Onglet 1. Trier les patients en P1, P2, P3 avec une justification, sur du matériel modeste. Un petit modèle (Qwen3-1.7B) entraîné sur une carte de 6 Go.

1:30 • Méthode

Données, SFT, DPO

Onglet 2. 5 000 cas FR/EN nettoyés et anonymisés, SFT puis DPO, choix sur la validation, mesure unique sur un test gelé : 90,66 % de F1, 7,2 % de sous-triage.

3:00 • Architecture

Du modèle au service

Onglet 3. Modèle fusionné et vérifié, servi par vLLM sur un GPU RunPod ; API FastAPI ; Docker ; CI/CD.

4:00 • Démo

Trois cas en direct

Onglet 4. Anaphylaxie (P1), poussée de BPCO (P2), mal de gorge en anglais (P3). Lire la priorité, l'explication, la recommandation et la latence renvoyées.

6:00 • Monitoring

Le service observé

Onglet 5. Les requêtes qui viennent d'arriver, la latence moyenne et p95, aucune erreur, API et vLLM disponibles. Aucune donnée patient dans les métriques.

7:00 • Limite

Le cas qui échoue

Onglet 4 puis 2. Douleur thoracique : le modèle écrit « suggests a heart attack » mais répond P2. Expliquer pourquoi (mots-clés, urgences dépendantes du temps trop rares).

8:30 • Conclusion

Second avis, pas décision

Le POC est faisable et industrialisable ; il ne doit pas trier seul. Proposition : second avis pour l'IOA, filet de sécurité par règles, évaluation sur cas réels.

06

Les questions probables

QuestionMa réponse courteOù le montrer
Pourquoi un si petit modèle ?Contrainte de la mission : entraînement sur 6 Go de VRAM et service peu coûteux. 1,7 milliard de paramètres en QLoRA tient sur ce matériel.SFT
Le score est-il fiable ?Test gelé de 500 cas jamais utilisé pour choisir, analyse de fuite, vérification après fusion (492/500 décisions identiques).Résultats
À quoi sert le DPO s'il ne change pas le triage ?La priorité est la même dans les deux réponses et s'annule dans la loss : le DPO ne règle que le style des explications, et l'effet mesuré est faible.DPO réaligné
Pourquoi rate-t-il l'infarctus ?Il a appris l'urgence à partir de mots alarmants ; infarctus et AVC sont rares dans le train et sans mot de gravité.Causes
Que se passe-t-il si vLLM tombe ?L'API renvoie une erreur 503 explicite, la disponibilité passe au rouge dans Grafana ; aucune priorité n'est inventée.Architecture
Et les données de santé ?Données publiques anonymisées (Presidio) ; en production : hébergement HDS, AIPD, contrôle humain.Synthèse
Combien ça coûte ?Moins de 0,60 $ de l'heure pour le GPU de démonstration ; l'API tourne sur CPU.Cloud

Si quelque chose ne marche pas

ProblèmeRéaction
Aucun GPU disponible sur RunPodEssayer une autre carte en Europe (A5000, L4, RTX 4000), sinon passer au plan B local.
vLLM ne démarre pasLire les logs (token Hugging Face, mémoire GPU) ; si ça dure plus de 10 minutes, plan B local.
L'API répond 503Vérifier VLLM_BASE_URL et la clé dans .env, puis docker compose up -d --force-recreate api.
Grafana videAttendre deux minutes après la rafale ; vérifier Prometheus › Targets ; recréer Prometheus si l'adresse du pod a changé.
vLLM « DOWN » dans PrometheusVérifier VLLM_METRICS_TARGET ; si la cible répond 401, l'expliquer et montrer seulement l'API.
Réseau coupéPlan C : captures d'écran et page Résultats.

08

Après la démo

1 · Couper le GPU

RunPod › Pods › Terminate (pas Stop) sur chaque pod, puis vérifier que la dépense horaire retombe presque à zéro.

2 · Arrêter le poste

docker compose --profile monitoring down, puis remettre INFERENCE_BACKEND=mock dans .env.

3 · Relever les chiffres

GPU, région, version de vLLM, temps de démarrage, latence moyenne et p95, résultat du test gelé en mode vLLM, captures Swagger et Grafana.

4 · Compléter la doc

Reporter ces chiffres dans Architecture, Résultats et le README, puis pousser.
