PRÉPARATION DE LA DÉMO

Tout ce qu'il faut lancer, ouvrir et dire,dans l'ordre.

Cette page est ma liste de contrôle pour la soutenance. Le modèle tourne sur un GPU RunPod derrière vLLM ; l'API et le monitoring tournent sur mon poste, branchés sur ce GPU. Je montre un parcours complet : un cas saisi dans l'API, la priorité et l'explication, le trafic qui apparaît dans Grafana, puis la limite connue du modèle. Compter 30 minutes de préparation et environ 1 $ de GPU.

02

Lancer le service, 30 minutes avant

Le démarrage de vLLM prend environ 3 à 8 minutes (image, puis 3,4 Go de poids depuis Hugging Face, puis préparation du GPU). Les commandes sont en PowerShell, depuis la racine du projet, dans une seule fenêtre gardée ouverte : les variables $env:VLLM_API_KEY et $POD disparaissent quand on la ferme.

T-30 • GPU

Déployer le pod vLLM

RunPod › Pods › Deploy : datacenter en Europe, RTX 4000 Ada (20 Go, environ 0,28 $/h) ou RTX A5000, On-Demand, template triage-vllm, Deploy. Noter l'heure, l'identifiant du pod et la région. Onglet Container logs (pas les logs système) : version de vLLM, puis Application startup complete.

T-20 • Contrôle

Vérifier que le modèle répond

Charger la clé sans l'afficher, définir $POD, interroger /v1/models : la réponse doit contenir "id":"triage-qwen3" et max_model_len 2048. Un 502 = pas encore prêt ; un 401 = clé différente entre .env et le secret.

T-15 • Poste

Lancer l'API et le monitoring

Renseigner dans .env l'adresse du pod (quatre lignes, hors écran), puis démarrer l'API, Prometheus et Grafana avec Docker Compose (--build pour embarquer le dernier code).

T-12 • Cloud (option)

L'API en ligne

RunPod › Deploy d'un pod CPU, template triage-api, Edit template : VLLM_BASE_URL = adresse du pod GPU + /v1. Vérifier /health (ok) et /version (…dpoaligned-ckpt200).

T-10 • Vérifier

Cibles et premier appel

Prometheus › Status › Targets : API et vLLM « UP ». La rafale des dix cas inédits réveille le service et remplit Grafana ; le journal d'audit doit montrer une ligne par appel.

T-5 • Onglets

Ouvrir les onglets dans l'ordre

Voir la section suivante. Se connecter à Grafana avant (le mot de passe ne doit pas apparaître), zoom du navigateur à 125 %, notifications coupées, terminal en grande police.

PowerShellà lancer dans l'ordre, une seule fenêtre
# 1. Clé vLLM chargée depuis .env, sans l'afficher (attendu ensuite : 40)
$env:VLLM_API_KEY = ((Get-Content .env | Select-String '^VLLM_API_KEY=').Line -split '=',2)[1]
$env:VLLM_API_KEY.Length

# 2. Adresse du pod GPU (l'identifiant change à chaque déploiement)
$POD = "https://<id-du-pod>-8000.proxy.runpod.net"

# 3. Le modèle répond ? (attendu : "id":"triage-qwen3")
curl.exe -s -H "Authorization: Bearer $env:VLLM_API_KEY" "$POD/v1/models"

# 4. Dans .env (notepad .env, hors écran) :
#    INFERENCE_BACKEND=vllm
#    VLLM_BASE_URL=https://<id-du-pod>-8000.proxy.runpod.net/v1
#    VLLM_METRICS_SCHEME=https
#    VLLM_METRICS_TARGET=<id-du-pod>-8000.proxy.runpod.net

# 5. API + Prometheus + Grafana sur le poste
docker compose --profile monitoring up -d --build api prometheus grafana

# 6. Santé et version de l'API (attendu : ok, model_ready true, …dpoaligned-ckpt200)
curl.exe http://127.0.0.1:8000/health
curl.exe http://127.0.0.1:8000/version

# 7. Rafale des dix cas inédits (remplit Grafana, sert de répétition)
uv run python benchmarks/demo_cas_inconnus.py --mode api --api-url http://127.0.0.1:8000

# 8. Journal d'audit : une ligne par décision, sans texte patient
docker compose exec api tail -n 3 /app/logs/audit.jsonl

Mesure de latence et test gelé du service (à faire une fois, hors démo, environ 5 minutes) : uv run python benchmarks/eval_test_gele.py --mode vllm --vllm-url "$POD/v1", d'abord avec --limit 20.

EN CAS DE PROBLÈME AU LANCEMENT Lire l'onglet Container logs du pod avant tout.

401 ou Repository not found au chargement : secret HF_TOKEN absent ou sans accès au dépôt. CUDA out of memory : GPU trop petit, en prendre un de 16 Go ou plus. Rien après 10 minutes : Terminate et redéployer sur un autre datacenter européen. Si le cloud reste indisponible, passer au plan B (modèle local).

04

Le déroulé, en dix minutes

0:00 • Contexte

Le besoin du CHSA

Onglet 1. Trier les patients en P1, P2, P3 avec une justification, sur du matériel modeste. Un petit modèle (Qwen3-1.7B) entraîné sur une carte de 6 Go.

1:30 • Méthode

Données, SFT, DPO

Onglet 2. 5 000 cas FR/EN nettoyés et anonymisés, SFT puis DPO, choix sur la validation, mesure unique sur un test gelé : 90,66 % de F1, 7,2 % de sous-triage.

3:00 • Architecture

Du modèle au service

Onglet 3. Modèle fusionné et vérifié, servi par vLLM sur un GPU RunPod ; API FastAPI ; Docker ; CI/CD.

4:00 • Démo

Trois cas en direct

Onglet 4. Purpura fébrile (P1), poussée de BPCO (P2), mal de gorge en anglais (P3). Lire la priorité, l'explication, la recommandation et la latence renvoyées.

6:00 • Monitoring

Le service observé

Onglet 5. Les requêtes qui viennent d'arriver, la latence moyenne et p95, aucune erreur, API et vLLM disponibles. Aucune donnée patient dans les métriques. Puis le journal d'audit dans le terminal : docker compose exec api tail -n 3 /app/logs/audit.jsonl, une ligne par décision, avec le même request_id que la réponse et une empreinte à la place du texte.

7:00 • Limite

Le cas qui échoue

Onglet 4 puis 2. Douleur thoracique : le modèle écrit « suggests a heart attack » mais répond P2. Expliquer pourquoi (mots-clés, urgences dépendantes du temps trop rares).

8:30 • Conclusion

Second avis, pas décision

Le POC est faisable et industrialisable ; il ne doit pas trier seul. Proposition : second avis pour l'IOA, filet de sécurité par règles, évaluation sur cas réels.

06

Les questions probables

QuestionMa réponse courteOù le montrer
Pourquoi un si petit modèle ?Contrainte de la mission : entraînement sur 6 Go de VRAM et service peu coûteux. 1,7 milliard de paramètres en QLoRA tient sur ce matériel.SFT
Le score est-il fiable ?Test gelé de 500 cas jamais utilisé pour choisir, analyse de fuite, vérification après fusion (492/500 décisions identiques).Résultats
À quoi sert le DPO s'il ne change pas le triage ?La priorité est la même dans les deux réponses et s'annule dans la loss : le DPO ne règle que le style des explications, et l'effet mesuré est faible.DPO réaligné
Pourquoi rate-t-il l'infarctus ?Il a appris l'urgence à partir de mots alarmants ; infarctus et AVC sont rares dans le train et sans mot de gravité.Causes
Que se passe-t-il si vLLM tombe ?L'API renvoie une erreur 503 explicite, la disponibilité passe au rouge dans Grafana ; aucune priorité n'est inventée.Architecture
Et les données de santé ?Données publiques anonymisées (Presidio) ; en production : hébergement HDS, AIPD, contrôle humain.Synthèse
Pourquoi pas Qwen3-1.7B-Base, comme prévu ?La version post-entraînée connaît déjà le format de conversation de l'API et de vLLM ; avec 4 000 exemples, l'entraînement sert au triage, pas au format. Pas de comparaison à protocole égal : c'est une limite assumée.SFT
Peut-on auditer une décision ?Oui : chaque appel laisse une ligne avec identifiant, horodatage, versions du modèle et du prompt, priorité et latence. Le texte du patient n'y est pas, seulement son empreinte.Architecture
Est-il prêt pour la production ?Le POC atteint ses onze objectifs. Avant déploiement, les cibles sont plus exigeantes : rappel P1 95 %, aucun P1 en P3, sous-triage 5 %, écart FR/EN 5 points, AIPD et HDS. C'est la marge de progression de la phase 0 et 1 ; d'ici là, pas de données réelles.Go / no-go
Où est le questionnaire adaptatif ?Hors du POC : le modèle classe un cas déjà décrit. Le test des cas inédits montre qu'un cas complet donne de meilleures réponses, d'où le questionnaire en feuille de route.Résultats
Combien ça coûte ?Moins de 0,60 $ de l'heure pour le GPU de démonstration ; l'API tourne sur CPU.Cloud
